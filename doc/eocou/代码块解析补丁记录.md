# eocou fork：代码块解析补丁记录（super_editor）

更新时间：2026-02-22  
分支：joe/code_parser

## 1. 为什么要改
在 eocou 的笔记编辑器里，代码块保存再解析时会出现不稳定行为：
- 连续代码内容会被错误拆成多个代码块。
- 典型数据形态（如 `{"insert":"\n\n\n","attributes":{"code-block":"plain"}}`）里，`c` 后的空行会掉成普通空段落，不在代码节点内部。

这不是数据脏，属于解析时“换行拆分后新段落默认是普通段落”导致。

## 2. 触发样例（简化）
```json
[
  {"insert":"a"},
  {"insert":"\n","attributes":{"code-block":"plain"}},
  {"insert":"b"},
  {"insert":"\n","attributes":{"code-block":"plain"}},
  {"insert":"c"},
  {"insert":"\n\n\n","attributes":{"code-block":"plain"}},
  {"insert":"\n\n\n\n"}
]
```

预期：仍是单个代码块（包含 `a\nb\nc`，并且后续空行语义稳定）。  
历史现象：在某些解析路径会被拆块。

## 3. 本次改动（仅 super_editor）
### 3.1 修改文件
- `super_editor/lib/src/infrastructure/serialization/quill/parsing/parser.dart`
- `super_editor/test/infrastructure/serialization/quill/parsing/multiline_parsing_test.dart`

### 3.2 parser 改动点
位置：`super_editor/lib/src/infrastructure/serialization/quill/parsing/parser.dart`

改动说明：
- 修复点前移到 `_doInsertText(...)`。
- 当当前段落“本次操作后实际生效的 `blockType`”是代码块，且 insert 含多换行时，换行拆出来的“中间新段落”也写入 `NodeMetadata.blockType = codeAttribution`。
- 最后一个占位段落仍保持默认段落（不改原有尾占位语义）。
- merge 阶段不再做代码块专用特判，继续使用通用 `blockMergeRules`。
- 关键约束：不再直接依赖 `hasAttribute("code-block")` 做硬判断，避免绕过 `blockFormats` 可配置机制。
- 兼容自定义格式：除了 `ChangeParagraphBlockTypeRequest`，还会识别 `ReplaceNodeRequest`（eocou 的语言代码块格式走这条）。

### 3.3 测试改动点
位置：`super_editor/test/infrastructure/serialization/quill/parsing/multiline_parsing_test.dart`

新增用例：
- `keeps a single code block when code newlines are compressed into one insert`
- `does not force code block when code format is not configured`

意义：
- 锁定 `"\n\n\n" + code-block` 的场景，防止未来升级回归。
- 锁定 `blockFormats` 可配置语义，防止“调用方没启用 CodeBlockDeltaFormat 也被强制解析成代码块”。

## 4. 升级上游时的冲突处理
升级 `super_editor` 时，优先关注：
- `super_editor/lib/src/infrastructure/serialization/quill/parsing/parser.dart`
- `super_editor/test/infrastructure/serialization/quill/parsing/multiline_parsing_test.dart`

处理建议：
1. 先看上游是否已经在 `_doInsertText(...)` 覆盖“code-block 多换行继承块属性”。  
2. 如果没有，保留本补丁（前置修复），不要回退到 merge 阶段特判。  
3. 运行测试（第 5 节）确认再合并。

冲突判定标准：
- 若上游改法能让本用例通过，可去掉本地实现。
- 若上游只改了部分逻辑，本地补丁继续保留。
